# Медиашлюз для RTSP: решение и план внедрения

Статус: отложенное проектное решение, шлюз ещё не запущен. 03.10.2026 задача C09 снята с текущего плана по решению владельца. В каталоге нет проверенного RTSP-источника с правом показа в LiveMap; RTSP не попадает в публичный API. Этот документ сохранён как справка для возможного возвращения к RTSP.

## Выбор

| Вариант | Для LiveMap |
| --- | --- |
| [MediaMTX](https://mediamtx.org/docs/read/web-browsers) | Первый кандидат: отдельный сервер, который принимает RTSP и отдаёт HLS или WebRTC. Подходит к существующему плееру HLS и уже описанным границам FastAPI/worker. У сервера есть фиксированные пути и режим подключения к источнику по запросу. |
| [go2rtc](https://github.com/AlexxIT/go2rtc) | Запасной вариант для камер, где нужна малая задержка и автоматический выбор WebRTC/MSE/HLS. Его [встроенный веб-плеер](https://github.com/AlexxIT/go2rtc/blob/master/www/README.md) можно оценить после появления конкретного источника и проверки кодека/браузеров. |
| [Restreamer](https://docs.datarhei.com/restreamer/knowledge-base/manual/video-player-settings) | Удобен, если оператору нужен отдельный графический интерфейс управления трансляциями. Для первых нескольких одобренных камер это ещё один интерфейс и процесс эксплуатации. |

MediaMTX и go2rtc могут передавать уже совместимые видеодорожки без перекодирования. **RTSP → HLS не гарантирует воспроизведение любого кодека**: для неподдерживаемой дорожки потребуется отдельный FFmpeg-процесс и оценка нагрузки. Наличие iframe или M3U8 также не подтверждает право LiveMap показывать чужую камеру.

## Предлагаемый путь первой камеры

1. Получить у владельца камеры адрес RTSP, место установки, условия публичного показа и контакт для удаления. Секреты не записывать в репозиторий, URL публичного API или query-строку плеера.
2. Создать **один фиксированный путь** в MediaMTX для одобренной камеры. Включить подключение к upstream по запросу и остановку после ухода зрителей. Не открывать API, позволяющий пользователю передать произвольный RTSP URL. Ограничить сетевой выход шлюза адресом согласованной камеры.
3. Отдать HLS по HTTPS через отдельный reverse proxy. Установить CORS для точного `PUBLIC_ORIGIN`; проверить манифест и сегменты. Начать с HLS, который уже воспроизводит `CameraPlayer.tsx`. WebRTC добавить для камер, которым важна меньшая задержка, после проверки ICE/TLS и браузеров.
4. Разделить в модели **приватный upstream** и **публичный playback URL**. Сейчас `Source.stream_url` выполняет обе роли, а правило публикации запрещает `rtsp` и `secret_ref`; его нельзя просто заменить RTSP-адресом. Админ API должен выдавать клиенту только безопасный HTTPS URL шлюза и атрибуцию владельца.
5. Worker должен проверять именно публичный HLS с origin LiveMap, а также получать внутренний сигнал о состоянии upstream. После ручной проверки реальных кадров публиковать камеру; при жалобе или потере разрешения снимать путь и маркер.

## Критерии приёмки

- Одна одобренная RTSP-камера воспроизводится в карточке LiveMap в Chromium и Firefox; маркеры не запускают поток до выбора камеры. Обязательная приёмка Safari/macOS исключена владельцем 03.10.2026.
- В публичном API, HTML, логах и дампе БД нет RTSP-пароля или временного токена; права на публикацию и контакт владельца сохранены в каталоге.
- Подтверждены HTTPS, CORS манифеста и сегментов, совместимый кодек, восстановление после обрыва, задержка и фактическая нагрузка при 1 и 20 зрителях.
- Остановка просмотра завершает ненужное подключение к upstream; удаление камеры закрывает публичный путь.

До выполнения этих критериев установленная программа-шлюз сама по себе не добавляет камеру на карту. Данные из случайных M3U/RTSP-плейлистов и систем «Безопасный город» проходят ту же проверку владельца и права на показ, что и любой другой источник.
